# Rex UI and installer design

This document is the design for step 6 of the [Rex host plan](PLAN.md): the Lua module, its palette actions and screens, and the installer. It also covers item 9 of PLAN's "Before the first release" and the install half of item 10. The step is done when a machine with Rex and no Herdr can install Namedrop, activate it, and name a pane from the palette.

The design is for the agent who implements step 6 and the person who reviews it. A person who uses Rex without Herdr gets what a Herdr user gets today: one install, an activation per space, and the naming, manage, Doctor, status, and tour screens from the palette and from keys. A person who runs Herdr inside Rex keeps one Namedrop, and both hosts use it.

The evidence comes from probes on 2026-11-14 with two Rex builds and two Namedrop builds. Rex `0.1.0-preview.14` (commit `7e460d0`, API revision 12) is the server the Rex app ran then. Rex `0.1.0-preview.18` (commit `baf79e0`, API revision 13, "supports 0 to 13") is the server the app bundle now ships, so the next server restart runs it. Namedrop ran as a debug build at `329c278b`, and as a scratch build of the same source whose handshake offers revisions 12 to 13. Every probe ran on a scratch Rex server with its own socket, state directory, and `HOME`, started under `env -i`. No probe touched the user's Rex server, `~/.config/rex`, or Herdr. [Evidence](#evidence) gives the commands. Each claim says whether it was measured, read in Rex's documentation, or inferred, and a claim measured by a review names the review. A measured claim holds on both Rex builds unless it names one.

The design branch is `exp/rex-ui-design`, cut from `origin/experimental` at `329c278b`.

Five facts about today's Namedrop on Rex matter as much as the Rex facts.

- **`activate` on a Rex endpoint writes Herdr's key bindings** (measured). It activated the session and installed both agent packages, and it also wrote five `[[keys.command]]` entries into `~/.config/herdr/config.toml` and reported `reloaded: true`. `activate` calls `shortcuts::activate_shortcuts` for every host (`src/lifecycle.rs:505-506`), and the Rex adapter answers `ReloadKeybindings` with `Applied::Unsupported`, which the shortcut code reads as success (`src/shortcuts.rs:209-215`, `src/mux/rex.rs:793-794`).
- **`ui launch` on Rex opens nothing.** The Rex adapter answers `OpenPopup` with `Unsupported` too, so `ui launch` returns `null` (`src/lifecycle.rs:1419-1422`). The first-agent tour then consumes its once-only marker and reports `shown: true` for a popup that never opened (`src/tour.rs:428-440`). The marker is claimed before the popup on purpose, so two agents found at once open one tour, and a failed open is not retried.
- **`scripts/runtime.py` calls `herdr` even where nothing else does** (measured by the second review). The first publish records the sessions of the one-time launcher migration through `update.session_panes()`, which runs `herdr session list` and reads `HERDR_SOCKET_PATH` (`scripts/runtime.py:94-108`, `:857`, `scripts/update.py:278-306`). An update that is not live or whose schema changes runs `update.preflight()`, which needs `HERDR_PANE_ID` and `HERDR_WORKSPACE_ID` (`scripts/runtime.py:820-825`, `scripts/update.py:309-338`). With a scratch state and no `herdr` on `PATH`, the script stops with `Namedrop runtime activation stopped: [Errno 2] No such file or directory: 'herdr'`, exit 2. That survey sees only Herdr servers, so Rex agents on a machine with both hosts are invisible to it.
- **Two runtimes can take turns owning the packages** (measured by the first review). Two copies of today's runtime, with one scratch `HOME` and the owner files the first draft proposed, activated A, then B, then A, and the install record followed each one. `package_guard()` locks and checks only the running runtime's own directory (`src/installed_runtime.rs:202-224`). Its callers are the package refresh (`src/install.rs:907`), `remove_subagent_hooks` in `deactivate` (`src/install.rs:1116`), the Codex sandbox in `name`'s auto-activation and in `activate` (`src/lifecycle.rs:273`, `:478`), and the sandbox and permission removals in `deactivate` (`src/install/codex_sandbox.rs:361`, `src/install/claude_permissions.rs:423`). `install_shell_command`, which writes `~/.local/bin/namedrop`, runs outside it (`src/lifecycle.rs:470`).
- **A process with an old state directory starts that state's helpers before any check** (read in the source, and measured by the third review, Codex's). A hook wrapper bakes `--state-directory <state>`, and Codex runs hooks from its own cached copy of the package, so a running agent keeps the old path after the package is rewritten. An explicit state wins over the install record (`src/locator.rs:180-210`). The hook forms start the reminder clock first (`src/main.rs:171-184`), and every Rex command calls `rex_bridge::ensure` before it opens the store or touches a package (`src/main.rs:1043`). `reexec_if_replaced` follows a replacement only inside the same state (`src/installed_runtime.rs:71-95`). The third review ran today's binary with an explicit old state while the record named a new one, and the old state's bridge lock appeared.

## How Herdr does it today

### The plugin manifest

`herdr-plugin.toml` declares Namedrop 1.7.9 for Herdr 0.7.5 or later, on macOS and Linux (`herdr-plugin.toml:1-6`). Herdr runs `[[build]]` (`scripts/build.sh`) after it clones the plugin, and `[[startup]]` (`run.sh reconcile`) when it starts. Every command below runs as `sh ./scripts/run.sh …`.

| Action | Title | Context | Runs | Opens |
|---|---|---|---|---|
| `activate` | Activate Namedrop | workspace | `activate --input-json {"confirmed":true}` | nothing, through `runtime.py` |
| `channels` | Open Namedrop Channels | workspace | `channels` | the browser |
| `name-agent` | Name this pane | pane | `ui launch name` | popup `naming`, 72x20 |
| `manage-addresses` | Manage Namedrop names and agents | pane | `ui launch manage` | popup `management`, 72x24 |
| `doctor` | Namedrop Doctor | pane | `ui launch doctor` | popup `doctor`, 72x24 |
| `check` | Check Namedrop health | workspace | `doctor` | nothing, a report |
| `agent-status` | Agent status | pane | `ui launch status` | popup `agent-status`, 84x24 |
| `tour` | Namedrop tour | pane | `ui launch tour` | popup `tour`, 72x24 |
| `deactivate`, `pause`, `resume` | Deactivate, Pause, Resume Namedrop | workspace | `deactivate`, `space pause`, `space resume` | nothing |
| `update` | Update Namedrop | workspace | `update.sh --open` | tab `update` |

Each popup is a manifest pane whose command is `ui run <mode>`. The tabs `setup` and `update` run `setup.sh activate --keep-open` and `update.sh`. Five lifecycle events run `event pane-lifecycle`, and `pane.agent_status_changed` and `pane.agent_detected` run `hook agent-status-changed` (`herdr-plugin.toml:133-163`). The manifest has no keys. Activation writes them into Herdr's own config.

### The scripts

- **`scripts/run.sh`** adds `--herdr-pane $HERDR_PANE_ID` when Herdr set it, sends `activate` to `runtime.py`, and otherwise runs the first of `$HERDR_PLUGIN_STATE_DIR/runtime/namedrop`, `bin/namedrop`, and the release build.
- **`scripts/build.sh`** builds `--release` for Darwin arm64 or Linux x86_64 and aarch64 and stages `bin/namedrop`. It contacts no host.
- **`scripts/setup.sh`** needs `HERDR_WORKSPACE_ID`, `HERDR_PANE_ID`, `HERDR_SOCKET_PATH`, `herdr`, and `python3` (`:28-39`). `install` links a local or archive checkout with `herdr plugin link`. `activate` invokes the `activate` action over Herdr's socket, polls the plugin log for 60 s, checks the space and the packages, and prints a human report.
- **`scripts/runtime.py`** publishes the runtime. Under `<state>/activation.lock` it checks `bin/namedrop --runtime-info` against `runtime.json`, copies the binary to `<state>/runtime/releases/<sha256>/namedrop`, writes the launcher `<state>/runtime/namedrop` that runs `current/namedrop`, switches the `current` link (migrating the store when the schema changes), runs `<launcher> activate`, checks that `space_id` equals `HERDR_WORKSPACE_ID`, runs `codex plugin marketplace add` and `codex plugin add namedrop@namedrop`, and restores the old runtime on any failure (`:807-921`). Its state is `HERDR_PLUGIN_STATE_DIR` (`:808`). It stops a helper only when that helper is a status worker of a retained release from before 1.7.0 that holds the command lock (`gate_helpers`, `:348-381`). Every later helper holds the gate only while it works, so activation waits for it and never stops it. The `HERDR_*` names in `helper_kind` and `queue_wake` (`:332`, `:433-438`) therefore matter only for those old workers, which never ran on Rex.
- **`scripts/update.py`** fetches the registered GitHub ref into a scratch checkout, validates its manifest with the launcher, waits for idle sessions, runs `herdr plugin install`, and runs the new `setup.sh activate`.
- **`scripts/check-update.py`**, embedded in the binary, asks `herdr plugin list` for the registration, runs `git ls-remote`, and reads the version from the manifest at that commit into `<state>/update-check.json`.
- **`scripts/package-release.sh`** builds the archive with `bin/namedrop`, the scripts, `runtime.json`, `SHA256SUMS`, and a `.tar.gz.sha256`. Nothing is signed.

### What a person does

1. `herdr integration install codex` and `herdr integration install claude`.
2. `herdr plugin install ericbust/namedrop --ref main`, which clones and builds. An archive instead runs `sh scripts/setup.sh install`.
3. Open the `setup` tab, which activates the workspace and waits for Enter.
4. Run `namedrop doctor` in a new tab, and start new agent sessions.

`activate` writes these files (`src/lifecycle.rs:452-524`, `src/install.rs`).

- `~/.local/bin/namedrop`, a script that runs the launcher with `--plugin-state <state>`, and a `PATH` line in the shell's startup file.
- `~/.claude/skills/namedrop/` and `~/.agents/skills/namedrop/`, each with `SKILL.md`, `tool.json`, both plugin manifests, `hooks/hooks.json`, the four hook wrappers, and an owner marker. Every wrapper bakes the launcher and `--state-directory <state>`.
- Claude Code allow rules in `settings.json`, Codex rules in `$CODEX_HOME/rules/namedrop.rules`, and the deferred-commands root in Codex's `config.toml`.
- The install record `~/.config/namedrop/state-directory`, which only a Rex home reads (`src/locator.rs:216-240`).
- Five `[[keys.command]]` bindings, `prefix+shift+{s,i,m,h,o}`, in Herdr's `config.toml`, then `herdr server reload-config`.

The update check runs at most once a day from `reconcile` and lifecycle events. A new version shows as Doctor's `ND-UPDATE-001` and as a once-a-day SessionStart message, both naming `herdr plugin action invoke update --plugin namedrop`.

### The screens

Each screen has two halves. `ui launch <mode>` runs in the person's pane, finds the target pane, and emits `Effect::OpenPopup`. Herdr renders that as `plugin pane open --placement popup` with `NAMEDROP_TARGET_WORKSPACE`, `_PANE`, `_TERMINAL`, `_SESSION`, `HERDR_PLUGIN_STATE_DIR`, and `HERDR_SOCKET_PATH` as `--env` values (`src/mux/herdr/wire.rs:682-732`). `ui run <mode>` is the popup's program. It reads the targets from its environment, refuses when the target pane's terminal changed, and runs a raw-terminal prompt through `/bin/stty` (`src/popup_input.rs`). The name, manage, Doctor, and tour screens are line prompts, and agent status is a live panel. None has a `--json` mode, because each is interactive. Their agent-facing equivalents are `name`, `address`, and `doctor`, which do. Channels is not a popup. It starts the dashboard server and opens the browser.

## Problem

Rex differs from Herdr in seven ways that shape this step.

- **Rex has no plugin manifest.** Actions and keys come only from the person's `init.lua`. Rex never runs a build, a startup command, or an event command for Namedrop.
- **Lua has no widgets.** A Rex action can run programs, call the API, and open blocks. It cannot draw text, read a line, or show a list, and the palette's handling of action arguments is undocumented. Every screen with input must be a program in a terminal.
- **A layer takes no environment.** Herdr's popup passes six values with `--env`. A Rex layer passes only argv and `path_prepend`.
- **An action runs in the server's environment.** It gets the server's `PATH`, not the person's shell, and a program in a layer gets a login `HOME` unless the layer sets `login = false`.
- **Nothing installs Namedrop.** No command puts the binary, the agent packages, or the Lua module on a machine without Herdr. Until U12, the testbed's Rex lane activated inside a profile Herdr and then stopped it (PORT.md, "Namedrop has no `integration install`"). U12 makes it install with the build's own `install.sh` and start no Herdr.
- **One machine can run both hosts.** The measured machine runs Herdr inside a Rex block. Both hosts write the same agent packages, which bake one launcher and one state directory, and Claude Code and Codex load one set of hooks.
- **A remote host is a second install.** Each machine that runs agents runs its own Namedrop beside its own Rex server (ADAPTER.md, "Remote hosts").

These constraints carry over from steps 4 and 5. Herdr behavior does not change, except for text that names the host and the differences each [H] commit pins. Every existing test passes.

## Shapes considered

Four whole shapes could put the screens into Rex.

**A. Lua screens over `namedrop --json`.** The module would run `namedrop … --json`, read the result, and show it. Lua cannot show it: no Rex Lua call draws text or reads input, and a palette action cannot ask for an alias in any documented way. The shape would give Rex a list action and a fixed-argument name action for keys, and no naming from the palette. It fails the done-when.

**B. Lua opens layers that run Namedrop's TUI.** Each action calls `rex.session.new_layer` with a command that runs `namedrop ui run <mode>` and passes the targets through `/usr/bin/env` in argv. The probe proved this works with today's binary. The cost is a second copy of `PopupSpec` in Lua: the target terminal and agent session, which the module cannot read, the screen sizes, the state directory, and the target checks that `ui launch` does. The tour that opens after activation, and any future popup Namedrop starts itself, would still need a Rust path to `new_layer`.

**C. Lua runs `namedrop ui launch`, and the Rex adapter opens the layer.** Each action is one `rex.exec` of `namedrop rex action <name> --endpoint <server> --space <ctx.session_id> --pane <ctx.block_id>`, which runs `ui launch <mode>` for a screen. The Rex adapter renders `Effect::OpenPopup` as `session.new_layer`, with the same targets and checks Herdr gets, in argv instead of `--env`. The Lua module holds a table of action names, titles, and keys, and nothing else.

**D. A Rex block plugin.** A Namedrop block type could draw its own screens. It needs `--block-dir` on the server's command line, which the app's server does not take from the person, and the docs describe nothing beyond the flag.

**Chosen: C.** It gives Rex every screen with one code path for both hosts. `ui launch` already finds the target, checks it, and emits `OpenPopup`, and `ui run` already reads its targets and refuses a changed pane, so the only new Rust is one adapter arm and the argv form of the targets. The tour after activation opens through the same arm. The module stays a table of names, and each action calls one Rust entry point, so a change to an action or a screen never touches Lua, and a module loaded before an update keeps working after it. The binary that the module runs generates it, with the launcher and state directory written in. The cost over B is one process start per action, 0.03 s for the whole `rex do` in the probe (measured, debug build).

## Design

### The Lua module

`namedrop install` writes `namedrop.lua` beside the `init.lua` that Rex reads, and inserts one line as the first line of `init.lua`:

```lua
pcall(require, "namedrop");
```

`pcall` keeps a missing or broken module from rejecting the person's whole file. The `;` keeps a file whose first line starts with `(` from turning the line into a call of `pcall`'s result. Both were measured. A broken module is then silent at load, so the installer and Doctor read back what loaded instead of trusting the reload's exit status.

The module holds only what every Namedrop release reads the same way: the launcher, the state directory, a table of action names, titles, and keys, an `endpoint()` helper, and one action, `namedrop_about`, that answers which module loaded. Each other action runs one Rust entry point, `namedrop rex action <name> --endpoint … --space … --pane …`. An update that changes what an action does, or how a screen opens, changes the binary behind the launcher and never the loaded Lua. A server that loaded the module before an update keeps working after it, with no reload.

The generated module looks like this, with the paths written in at install.

```lua
-- Managed by Namedrop. `namedrop install` rewrites this file, so edits here are lost.
-- A key bound later in init.lua wins over the same key below.
local NAMEDROP = "/Users/me/.local/state/namedrop/runtime/namedrop"
local STATE = "/Users/me/.local/state/namedrop"

local function endpoint()
	local status, err = rex.call("server.status")
	if status == nil then error("Namedrop could not ask Rex for its server: " .. tostring(err), 0) end
	for _, listener in ipairs(status.listeners or {}) do
		if listener.primary and listener.transport == "unix" then return "rex:" .. listener.addresses[1] end
	end
	error("Namedrop needs a Rex server that listens on a Unix socket", 0)
end

local actions = {
	{ "activate", "Activate Namedrop" },
	{ "name", "Name this pane", "alt+shift+cmd+i" },
	{ "manage", "Manage Namedrop names and agents", "alt+shift+cmd+m" },
	{ "doctor", "Namedrop Doctor", "alt+shift+cmd+h" },
	{ "status", "Agent status", "alt+shift+cmd+s" },
	{ "tour", "Namedrop tour", "alt+shift+cmd+o" },
	{ "channels", "Open Namedrop Channels" },
	{ "pause", "Pause Namedrop" },
	{ "resume", "Resume Namedrop" },
	{ "deactivate", "Deactivate Namedrop" },
}

for _, a in ipairs(actions) do
	local name, title, key = a[1], a[2], a[3]
	rex.action{ name = "namedrop_" .. name, title = title, category = "Namedrop", keywords = "namedrop mention agent",
		run = function(ctx)
			if ctx.session_id == nil or ctx.block_id == nil then error("Run this from a Rex pane", 0) end
			local argv = { NAMEDROP, "rex", "action", name, "--endpoint", endpoint(),
				"--space", ctx.session_id, "--pane", ctx.block_id }
			local result, err = rex.exec(argv, { env = { NAMEDROP_STATE_DIR = STATE }, timeout = 25 })
			if result == nil then
				if tostring(err):find("no such file or directory", 1, true) then
					error("Namedrop's launcher " .. NAMEDROP .. " is missing. Run sh scripts/install.sh again.", 0)
				end
				error("Namedrop's launcher " .. NAMEDROP .. " could not start: " .. tostring(err) .. ". Run sh scripts/install.sh again.", 0)
			end
			if result.ok then return end
			if result.timed_out then
				error(title .. " did not finish within 25 s, so Rex stopped it. If Namedrop is updating, try again when the update is done.", 0)
			end
			if result.stderr ~= nil and result.stderr ~= "" then error(result.stderr, 0) end
			if result.signal ~= nil then error(title .. " stopped on " .. tostring(result.signal) .. " before it finished.", 0) end
			error(title .. " exited with status " .. tostring(result.code) .. " and printed no reason.", 0)
		end }
	if key ~= nil and #rex.bindings{ key = key } == 0 then rex.bind(key, "namedrop_" .. name) end
end

rex.action{ name = "namedrop_about", title = "About Namedrop", category = "Namedrop",
	description = "Which Namedrop install this Rex configuration loaded",
	run = function()
		local env = {}
		for _, k in ipairs({ "HOME", "XDG_CONFIG_HOME", "XDG_STATE_HOME", "XDG_RUNTIME_DIR", "REX_SERVER" }) do
			env[k] = os.getenv(k)
		end
		return { module = debug.getinfo(1, "S").source, launcher = NAMEDROP, state = STATE, env = env }
	end }

rex.exec.start({ NAMEDROP, "rex", "ensure", "--from-server" },
	{ env = { NAMEDROP_STATE_DIR = STATE }, detach = true, stdout = false, stderr = false })
```

Seven choices in it need a reason.

- **One entry point.** `namedrop rex action <name>` maps the name to today's commands. `activate` runs a confirmed `activate`. `name`, `manage`, `doctor`, `status`, and `tour` run `ui launch <mode>`. `channels`, `pause`, `resume`, and `deactivate` run their commands. Each starts what its command starts: the reminder clock, as every command does, and, for `activate`, the deferred-command worker (the U6 review's F6). It prints a failure as one plain line on stderr, decoded from Namedrop's JSON envelope, and exits 1, so the palette shows `Error: <the line>` and never JSON. A run that leaves no such line is worded by the module itself, because Rex's own text for it is a bare `Error: ` or a raw spawn error (the U6 review measured both): Rex returns `nil` and `<path>: posix_spawn <path>: no such file or directory` for a missing launcher, which the module reports as `Namedrop's launcher <path> is missing. Run sh scripts/install.sh again.`, and any other start failure with Rex's reason and the same repair; a run past the 25 s limit returns `{ok = false, timed_out = true, signal = "SIGTERM", stderr = ""}`, reported as `<title> did not finish within 25 s, so Rex stopped it. If Namedrop is updating, try again when the update is done.`; and a run ended by a signal, or one that exits with an empty stderr, names the signal or the status. A name the binary does not know, as after a rollback to an older release, fails with `This Namedrop has no action <name>. Run sh scripts/install.sh again.` The module's text changes only when the list of actions does.
- **The endpoint comes from `server.status`.** Rex does not set `REX_SERVER` in every block, and an action's `ctx` carried no server (measured). The primary Unix listener is the canonical endpoint that `prove_local` already uses (ADAPTER.md, "The endpoint string carries the kind"). An explicit `--endpoint` decides the home with no socket probe, and the adapter still proves the server local before it types anything.
- **No revision check in Lua.** The Rust handshake is the only version gate. Its hello offers a range, and the server settles on the highest revision both support or closes the connection (measured), so every action and every CLI call is gated in one place, with one error. The tested range widens per release, after the probes of [What exists in Rex](#what-exists-in-rex) run on the new Rex build. Revision 13 joins it in U1: preview.18 differs from preview.14 only by the revision and one terminal action Namedrop does not use, and a build that offered 12 to 13 passed the same checks on both servers (measured).
- **Keys are bound by default, and a bound key is skipped.** The module binds `alt+shift+cmd+{i,m,h,s,o}`, Herdr's letters on the one modifier set the Mac app leaves free, unless `rex.bindings{ key = … }` already returns a binding for the key. That call sees only the bindings the file made before the module (measured), which on line 1 is none, unless the person moved the line down. A key the person binds later in `init.lua` wins, because Rex puts the newest binding on top (measured). Doctor reads `client.keymap` and reports each Namedrop key as in effect, or as shadowed with the source line that shadows it, and lists the keys not bound to Namedrop: skipped at load, or removed since with `rex.unbind`, which the keymap cannot tell apart. The bindings carry action names, so `rex keymap` shows each one with its source.
- **No palette action takes an argument.** The palette's handling of arguments is undocumented, and every input is read by a screen.
- **The module says which install it is.** `namedrop_about` runs no program. It returns the module's absolute path, the launcher and state written into it, and the server's `HOME`, `XDG_*`, and `REX_SERVER`. An action's `source` holds only the base name `namedrop.lua`, so the installer and Doctor run `namedrop_about` to prove that the server loaded this module, baked to this launcher and state (measured on a `--config` server, where the action listed `namedrop.lua:3` either way). Rex has no way to hide an action, so About Namedrop is in the palette too. `client.action` returns the action's value under `result`, beside `client_actions`, as `{"client_actions": [], "result": {…}}` (measured on preview.14, .18 and .19), so the readback reads `result`.
- **The last line starts the bridge at server start, behind a guard.** A remote host needs its bridge running before any agent there runs a Namedrop command (PLAN.md, "With B's bridge stopped, A keeps the item"). [The load-time start](#the-load-time-start) gives the guard.

### The load-time start

`namedrop rex ensure --from-server` starts the bridge when config code runs inside the server, and otherwise exits doing nothing. A top-level `rex.exec.start` also runs at `rex config check`, in the checker's environment (measured), and the guard keeps that run from starting anything.

The guard runs first in `main`, before the runtime, the store, the locator, or any home probe exists, so a refused run writes no file and calls no host. It finds the socket as `rex` does: `REX_SERVER` when it names a Unix socket, else Rex's default socket, which is `$HOME/Library/Application Support/rex/server.sock` on macOS and `$XDG_RUNTIME_DIR/rex/server.sock` on Linux. That is the rule `rex_claim` already applies (`src/mux/home.rs:346-370`). It connects, reads the socket's peer pid as `prove_local` does, reads its own parent pid at once, and continues only when the two are equal. Then it proves the server local, as `prove_local` does, and calls `rex_bridge::ensure` with the endpoint the server names itself by, its primary Unix listener, which is the endpoint every action passes as `--endpoint`. `ensure` is idempotent through the bridge lock (`src/rex_bridge.rs:137`), so a server whose `REX_SERVER` spells its socket another way than its listener, such as `/tmp` for `/private/tmp`, still runs one bridge, which the first action finds (the U6 review's F1). `namedrop rex ensure` is a new subcommand: today the `rex` group has only `bridge` (`src/cli.rs:499-501`), and the bridge starts as a side effect of other commands. The state directory it ensures is checked for retirement first ([Retiring a state](#retiring-a-state)).

The measured parents decide each case.

| Who ran the config code | Parent | Peer | Result |
|---|---|---|---|
| The server, at start or `config reload` | the server | the server | the bridge starts |
| `rex config check` | 1 | the server, or no socket | refused |
| A `rex do` script | 1 | the server, or no socket | refused |
| A server whose `REX_SERVER` names a forwarding socket | the server | the forwarder | refused |
| A server with no `REX_SERVER` and a socket that is not the default | the server | no socket | refused. The bridge then starts with the first Namedrop command in a block, as today |
| A program that an action runs | the server | the server | the bridge starts, or is already running |

This is a correctness guard, not a security boundary. Config code already runs programs as the same user, so a hostile `init.lua` needs no guard to start a bridge. The guard only keeps a checker's run, in the wrong environment, from starting one. On Linux, an orphan goes to the nearest subreaper rather than to pid 1. If the Rex server is a subreaper, a `config check` run inside a Rex block could see the server as its parent. That is measured before release ([Release checks](#release-checks)).

### Popups on Rex

The Rex adapter answers `Effect::OpenPopup` with `session.new_layer` and returns `Applied::Opened` with the reply (ADAPTER.md, answer 6).

```rust
// src/mux/rex.rs, apply
Effect::OpenPopup(popup) => {
	let request = json!({
		"session_id": popup.target.space.as_str(),
		"window_id": popup.target.tab.as_str(), // a Rex pane's tab is its window
		"bounds": popup.screen.rex_bounds(),     // a fixed fraction of the window for each screen
		"focus": true,
		"layout": {"block": {"flavor": "com.superlogical.terminal.shell", "options": {
			"shell": "none",
			"login": false,                       // keep the server's HOME, and no banner
			"command": popup_argv(&popup, &self.endpoint, launcher),
		}}},
	});
	connection.call("session.new_layer", &request).map(Applied::Opened)
}

// ["/usr/bin/env", "NAMEDROP_TARGET_WORKSPACE=…", "NAMEDROP_TARGET_PANE=…",
//  "NAMEDROP_TARGET_TERMINAL=…", "NAMEDROP_TARGET_SESSION=…", "NAMEDROP_STATE_DIR=<state>",
//  <launcher>, "--endpoint", "rex:<socket>", "ui", "run", <mode>]
fn popup_argv(popup: &PopupSpec, endpoint: &Endpoint, launcher: &Path) -> Vec<String> { todo!() }
```

`/usr/bin/env` carries the five values the Herdr popup gets with `--env`, so `ui run` reads them unchanged. The probe ran exactly this argv (measured). Its `--endpoint` keeps the popup's own `REX_BLOCK`, which names the layer, out of the home decision. `login = false` matters for the testbed, whose profile `HOME` differs from the account's, and it drops the "Last login" banner from the screen.

**Bounds.** Each screen has a fixed fraction of the window, centered: `{x = 0.2, y = 0.2, w = 0.6, h = 0.6}` for the name, manage, Doctor, and tour screens, and `{x = 0.15, y = 0.15, w = 0.7, h = 0.7}` for agent status. No Rex call measured in this design gives a window's size in cells: `session.view` gives layout rectangles in fractions, and `size` is a terminal option, not a reading (the fourth review). A screen in a narrow window wraps. Sizing in cells waits until Rex reports a window's size, and is deferred.

**One key-wait rule.** `ui run` on a Rex endpoint, after any refusal or error, prints it and waits for one key before it exits, however soon the failure came. The program is still running while it waits, so the layer stays open whatever Rex's `exit` option says, and the layer keeps Rex's default `exit`. A screen that ends normally exits at once, and the layer closes.

The rule covers the two refusals that come before any screen starts as well: the runtime command gate's, and a selected runtime that cannot start. Only `ui run` waits. `ui launch` and every other command keep exit 69 with no wait, and Herdr's popups keep today's exits. After the key, `ui run` exits 0. When no key can be read, as with stdin at end of file, it exits with the code it would have used, 69 for a refusal before the screen. While either of these two waits it holds no command gate: the gate's refusal never took it, and a runtime that cannot start drops it before the wait, so an update, the repair in that state, is not kept waiting by the open layer. A screen that has started holds the shared command gate until it exits, so its own refusal or error waits with the gate held, as any open screen does, and an update waits for that key. U7 and U10 take that up.

**A launcher that cannot start.** The layer's program is `/usr/bin/env`, which always starts, so a missing launcher would not fail `new_layer`: the layer would open with `env`'s message and exit 127, and stay open because the exit is quick (measured by the third review). So `ui launch` checks the launcher first. It must be a regular, executable file, or `ui launch` builds no request, and `rex action` reports `Namedrop's launcher <path> is missing. Run sh scripts/install.sh again.` in the palette. A launcher removed between that check and the spawn leaves the error layer with exit 127, which U5's test accepts as the only other outcome.

`ui launch` on Rex refuses three targets before it builds the layer request. Each refusal names its screen by the title that Herdr's menu (`herdr-plugin.toml`) and the palette use: Name this pane, Manage Namedrop names and agents, Namedrop Doctor, Agent status, or Namedrop tour.

- **A block in no window.** A layer floats over a window, and a detached block has an empty window id. `ui launch` refuses it before any request: `This pane is not in a window, so <title> cannot open over it. Open <title> from a pane in a window.`
- **A block whose foreground program is `herdr`.** A person who runs Herdr inside Rex and opens Rex's palette over the Herdr block would otherwise name the Rex block that holds Herdr. The refusal says to use Herdr's own screen: `This pane is running Herdr. Use Herdr's own <title>.` A Rex home prints this text on purpose, so the [Words](#words) test allows it.
- **A block whose foreground program is any other Namedrop program.** The process facts carry no argv (measured), so `ui launch` does not try to tell a screen from other Namedrop commands. It refuses a block whose `foreground.name` is `namedrop`, which a screen behind `/usr/bin/env` and the launcher shows (measured): `This pane is running Namedrop. Open <title> from <place>.`, where the places are the pane to name, a pane in the space to manage, the pane to check, the agent's pane, and a pane in the space, in the order of the titles above. `ctx.block_id` is usually the focused block, so a palette run from inside a layer would otherwise target the layer. A block whose foreground is a person's own `namedrop` command, mid-run, is refused too, which costs nothing: naming it is never the intent.

  The one Namedrop foreground allowed is the launch's own process: a `ui launch` typed in the target pane. Rex's `foreground` is the foreground group's leader, and its `name` is the executable's, not `argv0` (measured: a typed launch, one wrapped in `sh -c`, and both ends of a pipe each opened the layer, and a symlink named `namedrop` to `/bin/sleep` reported `name: sleep`). So a `foreground.pid` equal to the launch's own pid is allowed. That pid is only the launch's when the block is on the server's host. The server is proven local, but the block's host is not checked yet, so a block on another host whose pid equals the launch's would be allowed; the check is deferred ([Deferred](#deferred)). A launch started as a child of a foreground Namedrop has another pid and is still refused, which U6's `rex action` must respect: it runs `ui launch` in its own process, not as a child.

In a Rex session that is not active, the naming screen offers activation instead of refusing: `Namedrop is not active in this session. Press Enter to activate it, or Esc to cancel.` A session that was activated and then deactivated is not active. Esc names and activates nothing. Enter runs the confirmed activation without the first-agent tour, because the person is already in a screen, clears the offer from the screen, and continues to the name prompt. An incomplete activation, by the CLI's rule (an agent package that is not installed or reports an error), does not stop naming. The screen first prints `Namedrop is active, but part of its setup needs attention:`, one `<agent>: <error>` line for each such package (`<agent>: not installed` when it reports no error), and `Namedrop Doctor lists the repair.` The CLI's activate report is not reused, because it names Herdr commands. A Herdr space keeps today's behavior.

### Activation on Rex

`activate` stops writing Herdr's keys for a Rex home. It reports `shortcuts: {"status": "rex_module", "path": "<config dir>/namedrop.lua", "keys": […]}`, with the keys in effect from `client.keymap`, instead. With no `rex.json`, or with one whose module `namedrop_about` does not confirm, it reports `{"status": "no_module", "repair": "Run sh scripts/install.sh."}`. One unconfirmed case needs only a reload: the module that answered is the registered file, the eleven actions loaded, and the file now holds the text for `rex.json`'s launcher and state, while About still names older ones, as after a refresh rewrote the file. Activation then reports `{"status": "stale_module", "path": …, "repair": "Reload Rex's configuration with rex config reload."}`, and Doctor's `ND-REX-001` says the same instead of the reinstall (the U6 review's F7). The readback compares the module, the launcher, and the state as files, so two spellings of one path, such as `/tmp` and `/private/tmp`, confirm. `activate_shortcuts` returns an error for `Applied::Unsupported` rather than `reloaded: true`, so no host reports a reload that did not happen. `ui install-shortcuts` on a Rex home writes no Herdr file, and exits with an error that names `namedrop.lua` and Doctor's report of the keys.

Activation opens at most one layer. Today's `activate` already opens the first-agent tour when an agent is present and the tour's marker is unclaimed (`src/lifecycle.rs:509`). `namedrop rex action activate` opens Doctor only when no tour opened, and Doctor lists what remains, such as Codex's hook approval. Activation from the naming screen's offer opens neither. Herdr's `activate` does not change.

The tour keeps Herdr's marker rule: it claims the marker before the popup, so two agents found at once open one tour, and a failed open keeps the marker. On a Rex home, the tour opens only over an agent in a window. It skips detached agents, the pane a detection names included, and takes the first agent in a window instead. When every agent is detached, it reports `reason: "no_window"` and claims no marker. An `Unsupported` result releases the marker. With the adapter arm, Rex reports `Opened`, so that release applies only to a Rex server that cannot open layers. Rex produces no detection (`AgentDetected` is deferred, ADAPTER.md), so on Rex only the next `activate` tries the tour again, after either case. The tour still never shows twice.

### The installer

A person on a machine with Rex and no Herdr does four things.

1. Download the release archive and its `.sha256`, check it, and unpack it. Or clone the repository and run `sh scripts/build.sh`.
2. Run `sh scripts/install.sh` with Rex running. It shows what it will change and asks once.
3. Open the Rex palette in a pane and run **Activate Namedrop**. The tour or Doctor opens, and Doctor lists anything left, such as Codex's hook approval.
4. Run **Name this pane**, or press <kbd>Alt</kbd>+<kbd>Shift</kbd>+<kbd>Cmd</kbd>+<kbd>I</kbd>, in each pane to name, and start new agent sessions.

`scripts/install.sh` decides which runtime runs the install, and changes nothing before step 7.

1. **Platform.** It checks the platform as `build.sh` does.
2. **Python.** It runs `python3 -c 'import sys'` rather than `command -v python3`. On a Mac without the developer tools, `/usr/bin/python3` is a stub that is on `PATH` but fails and offers to install them, so only running it shows whether Python works. On failure it stops with `Namedrop needs Python 3. On macOS, install the Command Line Tools with xcode-select --install, then run sh scripts/install.sh again.`
3. **Rex.** `rex` on `PATH`, else `$REX_BIN_DIR/rex`. A plain login shell has neither (measured), so outside a Rex block it stops and names both ways to supply `rex`.
4. **The record.** It reads `$HOME/.config/namedrop/state-directory`. The record names a state directory `R` only when `R/runtime/namedrop` is a regular, executable file. A record whose launcher is missing is stale, and counts as no record.
5. **The owner.** The owner of a state directory is read one way everywhere, here and in `package_guard()`: `runtime/owner` when it exists; `herdr` when the directory has `runtime/current` and no `owner`, because every runtime published before this step came from Herdr; and none when nothing is published there.
6. **The decision.**
   - No record: a new install, into `NAMEDROP_STATE_DIR`, else `$XDG_STATE_HOME/namedrop`, else `~/.local/state/namedrop`, which is where `locator::state_directory` puts a Rex home with no record. That directory must have no owner or a `standalone` one. A Herdr-owned one stops the script with `ND-INSTALL-002`'s text. One that `install --remove` retired is installed again.
   - No record, and Herdr's Namedrop state owned by Herdr under the step-5 rule: a Herdr release from before step 6, such as 1.11.1, which writes no record. Without this check the script would make a second install beside it. Herdr keeps a plugin's state in `$XDG_STATE_HOME/herdr/plugins/namedrop`, else `~/.local/state/herdr/plugins/namedrop` (herdr's `config::state_dir` and `plugin_paths::plugin_state_dir`). The script reads that directory without running `herdr`, and stops with `Namedrop is already installed in Herdr (<dir>). Update Namedrop in Herdr first, then run sh scripts/install.sh again.` Updating writes the record, and the next run adopts. The signal is as good as the environment: a Herdr server started with another `XDG_STATE_HOME`, or a relative one, keeps its state where this check does not look, and the script then makes a new install as before.
   - `R` has a `herdr_handoff` marker in `runtime/retired.json`, which is checked before the owner: a handoff stopped part way ([Retiring a state](#retiring-a-state)). The script stops with `Namedrop is moving to Herdr. Run Activate Namedrop in Herdr again.`
   - `R` is `standalone`: an update of that install, in `R`.
   - `R` is Herdr's: adoption. It runs `R/runtime/namedrop --runtime-info`, whose contract gains `rex_ui` in U7. A launcher without it is a Herdr release from before step 6, with no `install` and no `rex action` (the first review measured `install --help` failing with exit 64 on such a copy), and the script stops with `Update Namedrop in Herdr first, then run sh scripts/install.sh again.` With `rex_ui`, adoption publishes no runtime, and leaves Herdr's runtime as it is even when the archive is newer. Herdr's updates update it.
7. **Confirmation and the runtime.** Before it asks, it runs the package's own binary as `namedrop --install-preview`, which reads no state, takes no lock, and writes nothing. The preview finds the Rex server by `namedrop install`'s own rule and reads `client.keymap` from it, so with `rex` on `PATH` and no server the script stops here, before any write, with `Namedrop found no running Rex server: … Start Rex, or set REX_SERVER to its Unix socket, then run sh scripts/install.sh again.` The preview also names everything `install` writes outside the state directory: the module, `init.lua` and its backup, `~/.local/bin/namedrop`, the startup files that get the PATH lines (`.zshrc` under zsh, `.bashrc` and a login file under bash, none otherwise, from `shell_startup_files`), `~/.agents/skills/namedrop`, `~/.claude/skills/namedrop`, the Claude permissions in `$CLAUDE_CONFIG_DIR/settings.json` (else `~/.claude`), `CODEX_HOME`, and `~/.config/namedrop`. `install` reports the same list as `targets`, from the same function, and `tests/rex_installer.py` checks every file it writes against the list. The script prints the decision (new, update, or adopt), the state directory, the Rex server, and that list, and asks once. `--yes` answers for the person. A new install or an update runs `python3 scripts/runtime.py <root> --state-dir <dir> --verify install`, which publishes the runtime, writes `owner` (`standalone`) and `source.json`, and runs `<launcher> install --input-json '{"confirmed":true}'`. Adoption runs `R/runtime/namedrop install --input-json '{"confirmed":true}'`, so the module is baked to Herdr's launcher.
8. **The report.** While `runtime.py` works, its progress lines reach the terminal. It then prints `namedrop install`'s report as plain lines: the module's path, the `init.lua` line's state, the same list of what was written, each key and whether it is in effect, the shell command with its PATH hint, and anything left, such as Codex's hook approval. A failed install prints the message of the binary's envelope, never the envelope. An interrupt at the prompt cancels with nothing changed, and a closed stdin answers no.

The runtime and the confirmed install put these on the machine.

`namedrop install` is a new command. It refuses without `--input-json {"confirmed":true}` and then lists every target, as `activate` does (`src/install.rs:203-226`). It shares `activate`'s package installer, which is already host-neutral, writes through the package lease ([One Namedrop](#one-namedrop-on-a-machine-with-both-hosts)), and activates no space. It refuses to replace a `namedrop.lua` whose first line is not its own. With `--print-config`, it writes `namedrop.lua`, prints the line and where it goes, and edits nothing else in Rex's config.

**Which server and which file.** The server decides which `init.lua` it reads, from `--config`, `REX_CONFIG`, and its own `XDG_CONFIG_HOME` and `HOME`, and the installer's environment can differ from the server's in each. So `namedrop install` asks the server. It finds the server as `rex_claim` does (`src/mux/home.rs:346-370`): `REX_SERVER` when it names a Unix socket, else Rex's default socket for the installer's `HOME`. It proves the server local as `prove_local` does. A server it cannot reach or prove local gets no edit, and the install asks the person to start Rex, or to set `REX_SERVER` to the server's socket, and run it again. It then reads `config.path` and `config.exists` from `client.keymap` on that server: the `--config` file, a link's own path, or the default path with `exists: false` (measured). `namedrop.lua` goes in that path's folder, which is where `require` looks, for a link too (measured). `rex.json` records the socket and both paths, so the package refresh, the handoff, Doctor, and `--remove` use the same server and the same files. The installer never runs `rex config check`, which resolves the path in the client's environment and runs the file's load-time code (measured). `config reload` is refused over a remote connection (Rex's docs), so the installer reloads only the local server it found.

**Editing `init.lua`.** The installer edits `init.lua` only under six guards, and otherwise prints the line, the reason, and where the line goes.

1. The path the server reports must be a regular file, or absent (`exists: false`), in which case the installer creates it with the line. For a symlink or any other kind of file, it prints the line. `namedrop.lua` still goes in the reported path's folder.
2. The line counts as present only as a whole line of its own, with surrounding spaces ignored. A comment or a string that mentions `require("namedrop")` does not count. A present line is left where it is.
3. `rex.json` records the line's state. `inserted` means this install added it, and only an `inserted` line is ever deleted. `present` means the person's own line was there first. `printed` means the installer printed the line instead of editing. `removed` means the line was `inserted` and is now gone: the person removed it, no later install or refresh adds it again, and Doctor reports it with the line to restore. No stored `removed` is trusted: the refresh, Doctor, the install, and `--remove` read `init.lua` again each time the state is `inserted` or `removed`. A read that finds the file without the line, or finds no file, makes it `removed`. A read that fails, as for a file Namedrop cannot read, changes nothing, so one failed read is never taken for a removal. The line back in the file, as the person adds it after Doctor's repair, makes it `inserted` again, so Doctor confirms it once Rex reloads, and `--remove` deletes it when it is line 1 (the U7 review's F1). A later install over `printed` looks again: a line now present becomes `present`, and an absent line is inserted when the guards now allow it, as after a link is replaced by a regular file, and printed again otherwise. A later install over `present` looks again too: the person asked to install, so a line of theirs that they deleted since is inserted, and is `inserted` from then on (the U7 review's F6).
4. The installer first takes the lease's verdict, so an install the lease refuses with `ND-INSTALL-002` reloads nothing, and releases the lease again. It then reloads the unedited file through `server.config_reload`. A reload fails only when its `diagnostics` hold an entry with `severity == "error"`. The status and the `generation` cannot tell, because a rejected reload returns status 0 and a higher generation, and a warning, such as a repeated action name, applies (measured). When the unedited file fails, it is already broken: the installer edits nothing, prints Rex's diagnostic and the line, and stops.
5. It copies `init.lua` to `init.lua.namedrop-<UTC time>.bak`, writes the new file through a temporary file and a rename, and reloads. It edits bytes, so a file that is not UTF-8, which Rex reads, is edited like any other. An edit that cannot be made, such as one whose backup or temporary file cannot be written, changes nothing and leaves no backup, and the install goes on as with `--print-config`: `init.lua`'s state is `printed`, and the report gives the line (`config_line`), the reason (`reason`), and where the line goes (`instruction`), as it does for every printed or removed line (the U7 review's F2). A file that cannot be read stops the install before any write, with an error that names the file and the line. When the reload fails, it checks that `init.lua` still holds the bytes it wrote, renames the backup back, reloads again, and reports Rex's diagnostic. A file the person changed in between is left as it is, and the report names both files. Once the reload passes, the edit stands, and it deletes the file's older backups, so only the newest is kept. A newer one, made by an edit still running, stays.
6. It confirms the install on the same server. `namedrop_about` must return `module` equal to `rex.json`'s module path, and `launcher` and `state` equal to this runtime's. `client.keymap` must list the eleven `namedrop_` actions. A reload with no error proves nothing here, because `pcall` hides a module error, and an action's `source` names only `namedrop.lua`, so it cannot tell two modules apart (measured). A failed readback fails the install and prints what `namedrop_about` returned. The edit stays, because the line is harmless without a working module.

The keys in effect come from `client.keymap`'s bindings, read after the reload: a Namedrop key whose top binding is not its `namedrop_` action is shadowed, and the report names the source line that shadows it. That holds for a binding whose action no file defines too: the newest binding wins, and what the client does with a binding to no action is unmeasured, because `client.key` from the CLI reaches only Lua bindings (the U6 review's F5). The install report and Doctor read them the same way, and `rex.json` stores none.

**Locks around the edit.** The package files, `namedrop.lua`, `rex.json`, and the `init.lua` write and backup happen under the package lease. The lease is released before each reload and before the readback, and is taken again only to restore a backup. A reload starts the module's load-time `namedrop rex ensure`, and a Namedrop command that an action or a refresh starts may want the lease, so a lease held while Rex works could leave each waiting on the other until Rex's 30 s action limit (inferred). Dropping it costs nothing: the readback checks the result.

**`scripts/runtime.py` becomes host-neutral.** It takes `--state-dir` and `--verify activate|install`. `run.sh` does not change, because of the rule below. An argv whose first word after ROOT is `--state-dir` is the explicit form, and must start `--state-dir DIR --verify activate`, in that order. Any other argv is run.sh's shape, `ROOT ARGUMENT...`, which `runtime.py` reads as `--state-dir "$HERDR_PLUGIN_STATE_DIR" --verify activate`, and that path keeps today's steps, its Herdr survey included: `record_legacy` through `herdr session list` on the first publish, and `preflight` before an update that is not live or that changes the schema. `--verify install` arrives in U8, after `install` exists. A mistyped explicit call, such as `--verify install --state-dir DIR`, is therefore read as run.sh's shape and acts on Herdr's state, as before U4. No caller makes one before U8, and `run.sh` only ever passes `activate …` or `--herdr-pane ID activate …`, so U8 refuses any other first word. `--verify install` makes no `herdr` call. It takes the migration record and the update preflight from two sources: the agent sessions the store holds for each endpoint, and a survey of the Rex agents through the incoming runtime, `<launcher> rex sessions --json`, which lists each Rex block's agent and session as the adapter's survey sees them. It then runs `<launcher> install` and checks `state_directory`, the packages, and `rex.json` instead of the space. Its standalone half, the survey, the refusal, and those checks, lives in `scripts/runtime_install.py`, which `runtime.py` imports only for `--verify install` and the archive carries beside it. The first publish's migration record leaves out a Rex agent that reports no session: only Namedrop's SessionStart hook binds one, so that agent never loaded a Namedrop hook, as with Claude Code or Codex started before the first install, which report their kind through OSC 7501. A later live update still waits for such an agent, because it cannot tell when the agent started. The preflight's refusal names each session it waits for, by alias, agent kind, status, block, and server, and each server it could not check. A live update waits only for the agents from before the install, and says that they still use pre-launcher tools or incomplete setup. An update that needs a session refresh waits for every open session and unfinished handoff, and says that it needs the refresh. Both modes refuse a state whose `runtime/retired.json` says `herdr_handoff`. `--verify install` sets a `removed` one aside, under the exclusive gate, only for the survey and the launcher's `install`, and removes it only when the install completes. An install that does not complete puts the marker back exactly as before, but "exactly as before" covers the marker only: a later failure comes after `install` registered the module, `rex.json`, and the packages ([Retiring a state](#retiring-a-state)). The first draft also taught `helper_kind` and `queue_wake` the neutral names, and stopped Rex helpers at publish. That half is dropped: a publish stops only status workers of releases before 1.7.0, which never ran on Rex, and waits for every later helper. The bridge and the relay worker already run the replacement runtime when they see one (ADAPTER.md, "The relay worker").

**`run.sh` stays byte for byte the same, in every release.** Every installed updater calls an update live only when the new `scripts/run.sh` is byte for byte the installed one (`prepare_target` in `scripts/update.py`). An edit to `run.sh`, a comment included, therefore makes the update to that release a session-refresh update for every installed updater. `tests/runtime_activation.py` pins its SHA-256 in CI, and `docs/releasing.md` states the rule.

Herdr's update preflight in `scripts/update.py` also counts the Rex-bound agent sessions in the store, so an update from Herdr on a machine with both hosts waits for Rex agents as it waits for Herdr's. It reads them from the store, because its Herdr survey cannot see Rex.

It counts an endpoint's sessions unless the endpoint's socket refuses a connection or is missing. That is a stopped server, which cannot record that a session ended, so its last sessions would otherwise block every update that waits for sessions. Any other failure counts the sessions, as the safe side: a denied socket, a timeout, or a key that is not an absolute socket path. Before "Ready to install." and while it waits, the updater names each stopped server it left out (`Not counted: the Rex server at … is not running, so its sessions have ended.`) and each server it could not check, with why (`Counted: could not check the Rex server at … (Permission denied), so its sessions count as open.`). `runtime.py`'s preflight prints the same lines to stderr. One case still reads as stopped: on macOS a server whose listen queue is full refuses a connection, as a stopped one does (measured on macOS; on Linux the connect blocks and times out, so the sessions count, read but not probed). Each counted session carries its alias, its registered runtime as the agent kind, and its last status, so a Rex Claude session is not taken for Codex. A session with no registration has no kind and is treated as Codex. A store whose schema the preflight does not know gives the preflight's schema message.

A Rust port of `runtime.py` would drop the `python3` requirement, which Herdr has too. This design keeps the script, because it is the one piece that must run outside the binary it replaces.

### One Namedrop on a machine with both hosts

The agent packages are one slot: `~/.claude/skills/namedrop`, `~/.agents/skills/namedrop`, `~/.local/bin/namedrop`, the install record, the Codex rules, and the Codex plugin name each hold one launcher and one state directory, and Claude Code and Codex load one set of hooks. Two installs cannot each own a copy without firing every hook twice. So one machine has one Namedrop: one state directory, one runtime, one set of packages. Both hosts' spaces live in one store, kept apart by the endpoint kind in `session_socket_id`, and each process resolves its host through `mux::home`. Before U12, the testbed's Rex lane ran this way: it activated in a profile Herdr, and its Rex blocks reached Herdr's state directory through the install record. Since U12 it runs the build's `install.sh` into `PROFILE/state/namedrop` with no Herdr (`testbed/README.md`, "The Rex lane").

**One lease.** `package_guard()` becomes the only way to write the shared packages. It returns a `PackageLease`, and every function that writes a package file takes `&PackageLease`, so a write outside the guard does not compile. The writers are:

- the package refresh that lifecycle events, `reconcile`, and the status worker run (`src/install.rs:907`). The status hook takes no package lock and writes no file of the slot. It queues its event and exits 0 whoever owns the packages, and its worker's refresh takes the lease. A standalone runtime's hook prints `ND-INSTALL-002` from a read without locks;
- `activate`'s packages, Codex sandbox root, and `~/.local/bin/namedrop` (`src/lifecycle.rs:470-478`). `install_shell_command` runs outside the guard today and moves under it. The activation report's `shell_command` is `null` when this runtime is no longer the selected one, and that runtime installs no shell command;
- the Codex sandbox root that `name`'s auto-activation writes (`src/lifecycle.rs:273`);
- `deactivate`'s removals of the subagent hooks, the sandbox root, and the Claude permissions (`src/install.rs:1116`, `src/install/codex_sandbox.rs:361`, `src/install/claude_permissions.rs:423`). `deactivate` takes the lease after the space deactivates. A lease error fails each removal, and the report still says `deactivated: true`. A removal never writes the record;
- `namedrop install`, `install --remove`, and the handoff.

`runtime.py`'s Codex registration, `codex plugin add`, names the package directory, which is the same path whatever the owner, and runs only after a launcher's `activate` or `install` passed the lease, so it needs no lease of its own.

Inside `package_guard()`, in this order:

1. It takes the per-user lock, `$HOME/.config/namedrop/packages.lock`.
2. It takes today's per-state lock, `<state>/runtime/packages.lock`, which still serializes `runtime.py`'s switch of `current` with a refresh inside one state.
3. It reads the install record, the owner of the state the record names (as in `install.sh` step 5), and that state's `retired.json`, and decides:
   - the record names this state: it writes, when this process is the selected runtime, as today;
   - no record, or a stale one: it writes, and the write records this state;
   - a Herdr-owned record, from a standalone runtime: it writes nothing and reports `ND-INSTALL-002`, which names Herdr's state directory;
   - a Herdr-owned record, from another Herdr state: it writes, and the write records this state, as Herdr's activation did before step 6;
   - a standalone record, from Herdr: it writes nothing. Herdr's `activate` hands off first ([Retiring a state](#retiring-a-state)) and then takes the lease again. Until the handoff arrives in U7, `activate` reports `ND-INSTALL-002` instead. Herdr's other writers (`name`, `deactivate`, lifecycle events, `reconcile`, the address commands, and the status worker) write nothing, report nothing, and still do their own work, so only `activate` reports `ND-INSTALL-002`;
   - a standalone record, from another standalone state: it writes nothing and reports `ND-INSTALL-002` with the recorded state;
   - a retired record whose `successor` is this state: it writes, which finishes a handoff that stopped part way;
   - a record whose state has a `removed` marker: it writes, as for a stale record, and the write records this state. A removal that stopped part way gives up the packages this way, and finds a new owner when it runs again ([Removing Namedrop from Rex](#removing-namedrop-from-rex)). This rule arrives with the marker in U7.

The last two rules are checked first. So the two standalone rules cover a standalone record that no marker retired, or that a handoff retired toward another state.

`ND-INSTALL-002` names the owner it found. For a Herdr owner it reads `Namedrop's shared agent packages belong to Herdr's install in <state>. Run Activate Namedrop in Herdr to update them.` For a standalone owner it reads `Namedrop's shared agent packages belong to the Rex install in <state>. Use that install to update them.`

The lease carries the verdict, so a writer that may not write returns its report without touching a file. A development build that runs outside a runtime directory keeps today's behavior and writes with no lock, as the tests do. A Herdr runtime run against another state directory writes as before step 6. A standalone runtime run against another state directory refuses with `the installed runtime does not belong to this state directory`. With no absolute `HOME` there is no package slot: the lease takes only the per-state lock and reads and writes no record.

**A per-user lock that cannot be opened.** `$HOME/.config/namedrop/packages.lock` can fail to open: its directory is read-only, `~/.config` is a file, or the path is not a regular file. A Herdr runtime then falls back to the per-state lock, as the no-`HOME` case does, and writes as it did before step 6. It still reads the install record and decides by the rules above, so a standalone record still makes it write nothing. It prints one line on stderr that names the path: `Namedrop could not open its package lock <path>: <error>. It wrote under the lock of <state> only.` A record it cannot write is a warning that names the record's path. The package installer warns so today (`src/install.rs:492-497`), but the lease writes the record first and returns the error (`src/installed_runtime/packages.rs:240-246`). So under the fallback, U7 turns the lease's record write into the same warning. The fallback is safe for the same reason a Herdr release from before step 6 is: each of the three causes holds for every process with this `HOME`, so no other writer can open the lock either, and a Herdr writer writes only in Herdr's favor. An error of one process alone, such as `EMFILE` when the process has run out of file descriptors, takes no fallback, because another writer may hold the lock meanwhile. That writer fails with `Namedrop could not open its package lock <path>: <error>.`, and a refresh skips as for a busy lock. Herdr's handoff takes no fallback either, because it needs the per-user lock to write `rex.json` in step 2 and the record in step 5. Before its first step, it opens the lock file without locking it. When that fails, the handoff stops and changes nothing, and the activation fails with `Namedrop could not open its package lock <path>: <error>.` A standalone runtime takes no fallback, because only the per-user lock keeps it from writing over Herdr's packages. Its writers fail with `Namedrop could not open its package lock <path>: <error>.`, and its refresh skips as for a busy lock. The fallback and the path in the error arrive in U7, with the `removed` rule. Built U3 fails Herdr's `activate` and `name` with the bare OS error, fails `deactivate`'s removals, and skips the refreshes of events and `reconcile` without a word, where the release before it wrote in each case (the U1 to U3 review).

**The refresh does not wait long.** The refresh that lifecycle events, `reconcile`, and the status worker run waits at most 1 s for the per-user lock. The wait polls every 20 ms and takes no turn behind writers that block on the lock, so while blocking writers keep the lock busy, every refresh can skip. When it cannot take the lock, because the lock is busy, or because a standalone runtime cannot open it, the refresh leaves the packages and only verifies them, as a replaced runtime does. A skipped refresh says nothing: it reports the packages as installed, and Doctor shows no package issue. The next writer that takes the lock writes them: the next activation, or the next refresh that gets the lock. Each lock holder is a short Namedrop writer that writes the packages itself, so a skip loses little. `activate`, `name`, the address commands, `deactivate`, and `namedrop install` wait for the lock. When a standalone runtime's refresh refuses, the refusal is its report: each agent runtime's package outcome carries `ND-INSTALL-002`, and the event still drains its mailbox, so the worker does not retry.

**Where the lock and the records live.** The packages are keyed by `HOME` alone: `$HOME/.claude/skills/namedrop`, `$HOME/.agents/skills/namedrop`, and `$HOME/.local/bin/namedrop`. Herdr's server and the Rex app's server can run with different `XDG_CONFIG_HOME`: Herdr's comes from a shell, whose startup file may set it, and the probe's Rex server had none (measured). So the per-user lock, the install record, and `rex.json` live in `$HOME/.config/namedrop/`, whatever `XDG_CONFIG_HOME` says, and every writer with one `HOME` takes one lock and reads one record. Today the record follows `XDG_CONFIG_HOME` (`src/locator.rs:199`, `src/install.rs:126-133`). It exists only on `experimental` and has never been released, so it moves with no migration. Two `HOME`s are two slots, as the testbed's profiles are. Claude Code's settings and Codex's rules follow `CLAUDE_CONFIG_DIR` and `CODEX_HOME`, and this design leaves them as they are.

**Lock order.** A process takes these locks only in this order, and never takes an earlier one while it holds a later one.

1. `<state>/runtime/activation.lock`: `runtime.py`, for its own state.
2. `<state>/runtime/commands.lock`, the command gate of a process's own state. Every other command takes it shared, and waits for it with no bound, with three exceptions: the dashboard server waits at most 60 s; `install --remove` from a standalone state takes it exclusively first, as below; and the subagent hook, the Stop hook, and the Stop worker take no gate, so an update never holds up an agent's turn, and each ends at its own short deadline. The long-lived helpers take it shared, with no bound, as commands do: the reminder clock, the deferred-command worker, and the relay worker when they start and around each round, the bridge when it starts and around each flush, and the status worker when it starts and around each event. Each checks the marker and the selected runtime again once it holds the gate. A gate it cannot take when it starts, as for a retired state or an interrupted update, ends it with exit 0 and no output (the U7 review's F7). Inside a round, a gate error ends the reminder clock and the deferred-command worker with no output, and the bridge, the relay worker, and the status worker leave that round's work for a later try, so each of them ends at its next check of the marker. No bound is needed, because no exclusive taker waits for a helper while it holds the gate, so a helper waits only as long as the gate stays held. Four takers hold it exclusively: `runtime.py`, around a switch and a migration (`command_gate`, `scripts/runtime.py:477-503`); `runtime.py` again, when a reinstall sets a `removed` marker aside; `runtime.py` a third time, when an install that did not complete puts the marker back exactly as before, which waits at most 5 s for the gate and then writes the marker without it ([Retiring a state](#retiring-a-state)); and `install --remove` from a standalone state, in place of the shared gate until it has written its marker, after which it takes the shared gate to stop the helpers ([Removing Namedrop from Rex](#removing-namedrop-from-rex)). A process that holds a state's shared gate cannot take that state's exclusive gate on a second descriptor until it releases the shared one: `command_gate` timed out against a held shared gate (measured by the fifth review). So each exclusive taker holds no shared gate of that state, and `runtime.py` releases its exclusive gate before it runs the launcher.
3. `<retiring state>/runtime/commands.lock`, exclusive: only the handoff, for the standalone state it retires.
4. `$HOME/.config/namedrop/packages.lock`: the per-user lock, inside `package_guard()`.
5. `<state>/runtime/packages.lock`: the per-state lock, inside `package_guard()` and `runtime.py`'s switch.

No process waits for a command gate while it holds the per-user lock. So a handoff that drains the old state and an old command waiting inside `package_guard()` cannot wait on each other: the handoff takes the per-user lock only after the drain, and while it then waits for the per-user lock with the old state's gate held, the holder of that lock waits for no gate. The per-user lock is never held across a Rex reload or a readback.

A Herdr release from before this step takes neither new lock. It can only write in Herdr's favor, which the rules allow, and the third case below covers what it misses.

**The module registration** lives in `$HOME/.config/namedrop/rex.json`, beside the install record, and not in a state directory. So it outlives any one state directory, and the runtime that owns the packages also owns the module. The owner's package refresh rewrites `namedrop.lua` at the recorded path, with its own launcher and state, when the text would change, and updates the launcher and state in `rex.json`, keeping `predecessors` as they are. `namedrop install` over an existing `rex.json` keeps them too. A refresh never edits `init.lua` and never reloads. A machine with no `rex.json`, or with a `rex.json` that names no module, never gets a module. The module is not an agent package, so a module the refresh cannot write, such as a `namedrop.lua` that is a symbolic link or is not Namedrop's, a module path that is relative or whose folder is gone, or a `rex.json` it cannot read, fails neither package: `activate` still exits 0 with both packages installed, and reports `rex_module: {"written": false, "error": …}` beside them (the U6 review's F2). Herdr's activation goes on past a `rex.json` it cannot read, unless a handoff must write its entry there. A handoff whose step 5 cannot rewrite the module leaves it naming the old launcher, so step 6 reports the module not confirmed with that error and seals nothing, without a Rex call, and the next activation tries again.

- **Herdr first, then Rex.** `install.sh` finds the record naming Herdr's state and adopts it (step 6). Herdr's updates then update both hosts, and the module follows through the package refresh.
- **Rex first, then Herdr.** Herdr fixes its own state directory, so its activation cannot adopt Rex's. It retires the standalone state and hands off ([Retiring a state](#retiring-a-state)). Names made on Rex before that stay in the old store, the handoff says so, and Doctor reports `ND-INSTALL-001` while agents still run the old hooks. Moving that store into Herdr's is deferred.
- **Rex first, then a Herdr release from before step 6.** That release rebakes the packages and its own record without the lock, and knows nothing of `rex.json`, so the module still names the standalone runtime. On Rex, Doctor compares the state the packages bake with `rex.json`'s state (`packages_bake_another_state`, which `install_record_mismatch` also uses, `src/install.rs:630-641`). When they differ, it reports `ND-INSTALL-003`: `Update Namedrop in Herdr, then run Activate Namedrop there again.` When `ND-INSTALL-003` fires, Doctor does not report `ND-INTEGRATION-002` beside it, because that repair, activating again on Rex, would take the packages back.

### Retiring a state

A standalone state stops being used in two ways: Herdr's activation takes the packages over, or `install --remove` removes them. The packages and the record then stop naming it, but a running agent's hooks still do, from Codex's cached copy of the package, and the old launcher stays on disk. Today such a hook starts the old state's reminder clock and bridge before any check (see the fifth fact in [What exists in Rex](#what-exists-in-rex)). So the old state is retired first, durably, and every Namedrop process checks for that before its first side effect.

**The marker.** `<state>/runtime/retired.json` holds `{"successor": "<state directory>" | null, "reason": "herdr_handoff" | "removed", "at": "<UTC time>"}`. It is written through a temporary file and a rename, then synced with its directory. A `herdr_handoff` marker is never removed, and that state is never used again: `runtime.py` refuses to publish into it, and `install.sh` refuses it (step 6). A `removed` marker is removed by the next confirmed install into the same state that completes, because a person who removes and then reinstalls wants the state back, and the hooks that still name it may then run again. Only two steps of the install need the state live, because `main` refuses a retired state: the incoming runtime's `rex sessions` survey and the launcher's `install`. So `runtime.py` checks the incoming contract, the executable, its `--runtime-info` and the snapshot, and finishes an interrupted migration, with the marker in place. It then renames the marker to `runtime/retired.aside.json` under that state's `activation.lock` and its command gate held exclusively, which keeps the marker's bytes and its `at`, syncs the file and the directory, and releases the gate before the survey and the launcher's `install`. The install completes when `runtime.py` exits 0: the launcher's `install`, its verification, and the Codex step passed. Then the set-aside marker is deleted.

On every other path the marker goes back, still under `activation.lock`: after a refused preflight, a failed survey, migration, `install`, or verification, a Codex step that fails, an exception, SIGTERM, or SIGHUP, which `runtime.py` turns into an exit that runs its cleanup. It takes the exclusive gate for at most 5 s and puts the marker back through a hard link, which never replaces a marker written since. So a `herdr_handoff` that Herdr's activation wrote while the state was live, or a `removed` from a new `install --remove`, stays, and the set-aside marker is dropped. A command that still holds the gate after 5 s, such as a screen opened during the install, does not stop the put-back: the marker goes back without the gate, and the install says that the command may still finish. A marker that cannot be written is named, with the state, in the install's output, after the error that stopped it. A marker left aside by a run that could not put it back, after SIGKILL or a power loss, is the install's intent, and the next `runtime.py` run puts it back first, unless a marker exists by then. Until that run the state is live, because Rust reads only `retired.json`. That is the residual.

"Exactly as before" covers the marker only. A failure after the launcher's `install`, in its verification or the Codex step, comes after `install` registered the module, `rex.json`, and the packages. They then name a retired state, whose actions answer `Namedrop was removed from Rex.` until the next install. A hook or command that started while the marker was aside has passed its check: a helper it started runs until its next gated flush, which exits it, and the subagent and stop hooks, which take no gate, finish their turn.

Removal leaves the store's bindings active, so a reinstall brings the sessions back. While the state is retired, no process records that one of those sessions ended, so a reinstall's preflight still counts it. A live reinstall waits only for sessions from before the first install. An update that needs a session refresh waits for each one, and its refusal names each by alias, agent kind, block, and server.

**The check.** One function, `installed_runtime::retirement(state)`. `main` resolves the state directory of every command form in one place and calls it there, before the form's first side effect. That covers the hook forms, which today start the reminder clock first (`src/main.rs:171-184`); the bridge, the relay worker, the status worker, and the dashboard server; `rex ensure --from-server`; and every command that builds a runtime, before `rex_bridge::ensure` (`src/main.rs:1043`). `command_guard` checks it too, after taking the gate, as it checks `migration.json` today (`src/installed_runtime.rs:65`), so a long-lived helper that takes the gate around each flush exits at its next flush. A retired state answers each kind of process its own way.

- A hook exits 0 with no output, and writes no file and starts no process. A hook must never fail an agent's turn.
- A command prints one line and exits 69: `ND-INSTALL-001`'s refusal form after a handoff, and `Namedrop was removed from Rex. Run sh scripts/install.sh to install it again.` after a removal.
- A helper exits at once.
- `install --remove` passes a `removed` marker and runs, so a removal that stopped part way finishes when the person runs it again. On a `herdr_handoff` marker it refuses like any command.

Forwarding to the successor was weighed and rejected. The successor's store holds none of the old sessions or names, so a forwarded hook would act on a session that is not active there, and the agent must restart to load the new hooks anyway.

**The handoff** runs in Herdr's `activate`, before it takes the lease, in two cases. Either the record names a standalone state `S`, or `rex.json` holds an unsealed `predecessors` entry for a state `S` whose marker is a `herdr_handoff` toward this state. The second case is a handoff that stopped after step 3, or whose step 6 could not confirm the module, perhaps after a Herdr writer took the record through the lease's rule for a record retired toward this state, and it starts at step 4. The handoff reads the record without the per-user lock, because step 1 waits on a command gate, and the lease reads it again in steps 2 and 5. When the per-user lock cannot be opened, the handoff does not start, and the activation fails ([One Namedrop](#one-namedrop-on-a-machine-with-both-hosts)).

1. It takes `S/runtime/commands.lock` exclusively, with the per-user lock not held, and waits at most 60 s for `S`'s running commands to finish. An open Namedrop screen of `S`, such as the tour that `S`'s activation opened, is one of them: its `ui run` holds `S`'s shared gate for as long as its layer is open (measured by the U5 review). The handoff never stops a screen, because the person may be typing in it. Past 60 s, activation fails with `Namedrop on Rex is busy. Close any Namedrop screen that is open in Rex, such as the tour, then run Activate Namedrop again.` and changes nothing. It then reads `S`'s marker again, as removal does after its gate.
   - No marker: it goes on to step 2.
   - A `herdr_handoff` marker toward this state: it releases the gate and goes to step 4.
   - A `removed` marker: a removal of `S` ran. The handoff releases the gate, retires nothing, and adds no entry. The lease then treats the record as stale and writes ([One Namedrop](#one-namedrop-on-a-machine-with-both-hosts)).
   - A `herdr_handoff` marker toward another state: it releases the gate, and the lease writes nothing, by its standalone rule.
2. It takes the lease and writes `S`'s entry in `rex.json`'s `predecessors`: `{"state": "<S>", "sealed": false, "agents": [{"endpoint": …, "block": …, "agent": "<pid>@<start>"}, …]}`, one agent for each session binding under `S/rex/sessions/`, with the binding's agent incarnation. The entry replaces any entry for `S`. A binding that the handoff cannot parse adds no agent, and the activation report names its path. With no `rex.json`, because the person deleted it or because `S` was activated on Rex but never installed, the handoff writes one that holds only `predecessors`. The lease's verdict here is to write nothing, by its rule for a standalone record from Herdr. The `predecessors` write does not depend on that verdict: the handoff takes the lease for its locks, writes only `rex.json`'s `predecessors` under it, and writes no package file and no record. It then releases the lease, and still holds `S`'s gate, so no `S` command runs meanwhile. No `S` hook can bind an agent between steps 2 and 3 either: bindings are written only by the SessionStart and UserPromptSubmit hooks, which wait for `S`'s shared gate (`src/mux/home.rs:150`, `src/main.rs:250-253`), and get it only after the marker, when they refuse.
3. It writes `S/runtime/retired.json` naming Herdr's state, and releases `S`'s gate. From here every `S` process refuses, those queued on the gate included. Because step 2 came first, `rex.json` names `S` before any writer can take the record from it.
4. It stops `S`'s helpers that hold no gate between flushes: the bridge, the relay worker, the deferred-command worker, the status worker, the reminder clock, and the dashboard server, each found through its lock file and checked by argv and state directory before any signal. One it misses exits at its next gate check.
5. It takes the lease and reads the record again. It rewrites the packages, the record, `namedrop.lua`, and `rex.json`'s launcher and state to Herdr's launcher and state, and keeps `S`'s entry as step 2 wrote it. No `S` process writes a binding after step 2, so the entry needs no second read. When the record already names this state, because a Herdr writer took it in between through the lease's rule for a record retired toward this state, the handoff still goes on. When `rex.json`, or `S`'s entry in it, is gone, the Rex half was removed after step 2: an `install --remove` from Herdr's launcher deleted `rex.json`, or the person did, and a later install may have written a new one. The handoff then writes no entry, and it writes no `rex.json` and no module when the file is gone, so `ND-INSTALL-001` stays cleared, as [When it clears](#retiring-a-state) says.
6. It releases the lease, and confirms the module on the server that `rex.json` names. Step 6 never fails the activation, so `runtime.py` never restores the previous runtime for it. Its Rex calls share one budget of 5 s, whatever `NAMEDROP_REX_TIMEOUT_MS` allows a single request (up to 60 s, `src/mux/rex/control.rs:16-17`). The budget stays well under 20 s because `runtime.py` runs `activate` a second time after `codex plugin add`, with `timeout=20` (`scripts/runtime.py:880`). A timeout there returns 1 and restores the previous runtime (`scripts/runtime.py:804`, `:890`), and since a handoff rebakes the Codex package, that second run is the usual case for a Codex user. When the budget runs out, the entry stays unsealed, as for a call that times out. With no entry to seal, step 6 does nothing. Otherwise it ends one of three ways.
   - `rex.json`'s line state is `printed` or `removed`, `rex.json` names no server, or nothing listens on the socket it names, because the socket file is missing or the connection is refused: it marks `S`'s entry `sealed` at once. With `printed` or `removed`, the server loads no module, so `namedrop_about` can never answer, and a line the person adds later loads the new `namedrop.lua`. A server that is not running reads the new `namedrop.lua` at its next start, so it needs no reload.
   - The server is reachable and local: it reloads that server and reads back `namedrop_about`, as the installer does. When the readback passes, it marks `S`'s entry `sealed`.
   - Any other failure: the server cannot be proved local, a call fails or times out, the budget runs out, the reload fails, or the readback disagrees. The entry stays unsealed. The activation report says that the module is not confirmed, with Rex's diagnostic or what `namedrop_about` returned, and the next activation runs steps 4 to 6 again.

   Each `sealed` write takes the lease again and reads `rex.json` again. Like step 5, it never recreates an entry or a file that was removed meanwhile, and the report then says `removed`, never `sealed`.

Each step reads what exists. A run that stops after step 2 leaves an entry whose state is not retired. That entry counts nothing, and the next activation starts again at step 1, because the record still names `S`. Its step 2 replaces the entry, so an agent that bound in between is counted. A run that stops after step 3 leaves the entry unsealed, so the next activation runs steps 4 to 6, whoever holds the record by then. A Rex action in between runs `S`'s launcher and shows `ND-INSTALL-001`. Each activation that runs step 5 for `S` says in its report that the names made on Rex stay in `S` and were not carried over. A handoff that is not stopped and whose step 6 seals the entry runs step 5 once, so the person reads the notice once, and a run that stops after step 3 cannot lose it. While the entry stays unsealed, as with an `init.lua` whose every reload fails, each activation runs steps 4 to 6 again, and its report repeats the notice beside the line that says the module is not confirmed.

`ND-INSTALL-001` has two forms. A retired state's command prints the refusal form, and makes no Rex call: `Namedrop on Rex moved to Herdr's install in <Herdr's state>. In each Rex session, run Activate Namedrop again and name the panes again, then restart the agents there so they load the new hooks.` Herdr's Doctor prints the warning form, with `1 agent on Rex still runs` for one agent and `<n> agents on Rex still run` for more: `Namedrop on Rex moved to Herdr's install in <Herdr's state>. <n> agents on Rex still run the old hooks from <S>, and the names made there were not carried over. In each Rex session, run Activate Namedrop again and name the panes again, then restart those agents so they load the new hooks. This warning clears when they have all ended.` Under it, one line per running agent names the block and the server as the entry recorded them: `<block> on <endpoint>`.

**Finding the old state after the handoff.** Herdr's Doctor finds `S` only through `rex.json`'s `predecessors`, and never through its own environment or a default path, because `S` can be any `NAMEDROP_STATE_DIR` and no process after a restart inherits it. It counts an entry only when that state's `retired.json` says `herdr_handoff` and names this state as `successor`. So an entry whose handoff stopped before its marker, a state that a removal retired, a state that names another successor, and a state directory that is gone count nothing. Doctor never reads `S`'s store, which stays at `S`'s schema.

**Which agents still run.** Doctor reads each agent of a counted entry as the Rex survey reads a binding's agent: a local read of its incarnation through `mux/processes.rs` (ADAPTER.md, "The incarnation is a pid and a local start time"). Only a process that reads `Alive` with that pid and that start time is running, as the survey counts a bound agent (`lives`, `src/mux/rex/agent.rs:182-188`). Everything else means the agent ended: no process, a zombie, another start time, and a process it cannot read. Every recorded agent is a local process of the person's own: a binding's agent is the binding hook's own ancestor, read `Alive` when it bound (`src/mux/rex/binding.rs:357-371`). The person's own process reads, even from inside Codex's sandbox (ADAPTER.md, "The incarnation is a pid and a local start time"). So a pid that reads `Unreadable` belongs to another user's process now. On macOS, that is the read of a root or system process that took the pid (`src/mux/processes.rs:108-122`). Counting it as running would bring a cleared warning back, with a repair the person cannot do. The check makes no Rex call, so it gives the same answer when the server that `rex.json` names is down, unreachable, or not provably local. A restart of that server ends every block's program (ADAPTER.md, "Restart detection"), so its agents read as ended afterwards.

**When it clears.** `ND-INSTALL-001` clears when every agent of every counted entry has ended. The warning's repair, restarting those agents, does that, and so does a restart of the Rex server. It also clears when `S`'s directory is deleted, and when `install --remove` deletes `rex.json`, because its repair, activating on Rex again, no longer applies. A cleared warning stays cleared. Once `S`'s marker is written, nothing adds an agent to its entry, and the handoff never writes an entry into a `rex.json` that lost it (step 5). An ended incarnation never runs again, because a new process with the same pid has another start time, and a pid that another user's process took reads as ended. So Doctor never writes `predecessors`, and an entry that counts nothing stays in the file and costs one read.

### Removing Namedrop from Rex

`namedrop install --remove` undoes the Rex half. It deletes line 1 of `init.lua` only when that line is exactly the line it inserted and `rex.json` says `inserted`, as `init.lua` reads now, with the same backup, reload, and restore as the install. Like the install, it first reloads the unedited file, with no lease held. Only an error its own edit made stops it: when the reload after the edit fails and the unedited file passed, it restores the backup and fails. When the unedited file already failed, the error is not removal's, so it goes on and its report names Rex's diagnostic in `config_error`. A reload that fails when removal made no edit never stops it (the U7 review's F5). It deletes `namedrop.lua` only when the file's first line is the managed-file line, and then deletes `rex.json`. With a `standalone` owner, it retires the state first, as the handoff's steps 3 and 4 do, with no successor and no `predecessors` entry and behind the gate below, so the standalone bridge, relay worker, and other helpers stop and cached hooks stay quiet. It then removes the agent packages, the permissions, the Codex rules and plugin, `~/.local/bin/namedrop`, and the install record under the lease. With a Herdr owner it removes only the Rex half, because Herdr still uses the rest, and says so. It never deletes a state directory. A full uninstall command for both hosts stays deferred.

Removal retires the state it runs from, so it cannot take that state's gate the way the handoff takes another state's. `main` reads the owner of the command's own state before it takes any gate. For `install --remove` with a `standalone` owner, `main` takes `commands.lock` exclusively, on its own descriptor, in place of the shared gate that every other command takes, and never holds the shared gate while it holds the exclusive one. It waits at most 60 s for the state's running commands to finish, an open Namedrop screen of the state included, as in the handoff's step 1. Past that, removal fails with `Namedrop on Rex is busy. Close any Namedrop screen that is open in Rex, such as the tour, then run namedrop install --remove again.` and changes nothing. Once it holds the gate, it checks the marker again and writes `retired.json` with `reason` `removed`. It then releases the exclusive gate and takes the shared gate on a new descriptor, so the process never holds both. A reinstall clears the marker only under the exclusive gate, so while removal holds the shared gate the marker cannot change. Under the shared gate, removal reads its marker again, stops the helpers only while the marker still says `removed`, and releases the gate. It then takes the lease for the rest. With a Herdr owner it retires nothing, and takes the shared gate as other commands do.

Removal holds no gate after it stops the helpers, so a handoff, a reinstall, or another writer can run between its steps. They meet only through the lease. Each time removal takes the lease, it reads its marker and the record again, and goes on only while the marker still says `removed` and the record names its state or no state.

- **The marker is gone.** A reinstall cleared it, under the exclusive gate that removal no longer holds, either before the helper stop or before a lease. Removal stops, changes nothing more, signals no helper of the reinstalled state, and says that Namedrop was installed again. Removal also reads the marker once with no lease held, before it reloads the unedited file, so a removal that a reinstall stopped while it waited sends Rex no reload.
- **The marker says `herdr_handoff`.** A reinstall cleared the marker, and a handoff then retired the state toward Herdr. Removal refuses as any command does on that marker: it prints `ND-INSTALL-001`'s refusal form, exits 69, and changes nothing more.
- **The record names another state.** Herdr's activation, or another writer, took the packages through the lease's `removed` rule. A handoff over a `removed` marker retires nothing and adds no `predecessors` entry (step 1 of [the handoff](#retiring-a-state)). Removal leaves the agent packages, the permissions, the Codex rules and plugin, `~/.local/bin/namedrop`, and the install record to that owner, removes only the Rex half, and says so, as with a Herdr owner.

### Updates

A standalone install has no Herdr registration, so `check-update.py` learns its source from `source.json`. For an archive or a GitHub checkout it lists the repository's `v*` tags with `git ls-remote --tags` and records the newest. On a Mac without the developer tools, `/usr/bin/git` is a stub that fails and offers to install them, so before it runs that `git` the check runs `xcode-select -p`, and when that fails it records `{"status": "skipped", "reason": "developer_tools_missing"}` and runs nothing. Doctor's `ND-UPDATE-001` and the SessionStart notice then say `Update: download Namedrop <version> and run sh scripts/install.sh`, and Herdr installs keep today's text. The SessionStart wrapper accepts either text by exact pattern, as it accepts one today (`src/install.rs:1315-1357`).

A standalone install's update setting lives in `~/.config/namedrop/settings.json`, with the same `check_for_updates` key as Herdr's `~/.config/herdr/plugins/config/namedrop/settings.json` (`src/update_check.rs:27-54`). The owner decides which file is read, so a machine with both hosts has one setting, in the owner's place.

Running `install.sh` from the new archive publishes the new runtime, refreshes the packages and the module, and reloads Rex's config. An archive whose state schema differs migrates the store through `runtime.py`, as Herdr's updates do, behind the store-and-Rex preflight above. A failure is undone by phase, through today's `restore` (`scripts/runtime.py:640-655`), and the design keeps its safety rule.

An open Namedrop screen holds its state's shared gate for as long as its layer is open (measured by the U5 review), as a Herdr popup does. `runtime.py` takes `command_gate` only for an update that changes the schema, around the switch and the migration (`scripts/runtime.py:587`, `:603`, `:859-863`). The gate waits 20 s for the screen and never stops it. Past that, an update that changes the schema stops before the switch, in the first row below, with today's `busy_gate_message`: it names the screen's pid and says to close the open Namedrop popup, such as the tour, and retry (`scripts/runtime.py:169-190`). `current` and the store are unchanged, and the new release stays unpacked in `releases/<digest>` (`scripts/runtime.py:847`). An update with the same schema takes no gate: it switches under the per-state `packages.lock` alone and goes on, and the open screen keeps running its old runtime until it closes. Herdr's updates already behave this way.

| Where the update failed | What stays selected | What `install.sh` says |
|---|---|---|
| Before the switch: the preflight, the contract check, or an inconsistent snapshot | The previous runtime. Nothing changed but the incoming release, which stays unpacked | The refusal, and that nothing was changed |
| After the switch, with the same schema: `install` or the readback failed | The previous runtime, switched back | `Installation did not complete. The previous runtime remains selected; existing sessions can continue.` |
| After a migration committed: the schema is the new one | The new runtime. `restore` will not select an old executable over migrated state | `restore`'s own warning, `Activation failed after a possible state migration. The new runtime remains selected; …`, and exit 1 |
| During the migration: `migration.json` is still there | Neither. Commands refuse until the next run's `recover_migration` finishes | `Namedrop installation was interrupted. Run sh scripts/install.sh again to finish; …`, and the next `install.sh` resumes |

The module names the stable launcher, so in each row it runs whatever runtime stays selected, and needs no rewrite. The third review ran `restore` against a scratch store already at the incoming schema: the new runtime stayed selected, and the warning printed. An update command that downloads and checks the archive itself is deferred.

In a state that `install --remove` retired, every row keeps the `removed` marker exactly as it was, and the install says `Namedrop stays removed from Rex.` in place of the second row's words ([Retiring a state](#retiring-a-state)).

A first install has no previous runtime, so its migration record names none, and a retry could only run the same target again. So when a first install's migration fails and leaves the store's schema as it found it, or leaves no store where there was none, the install selects nothing and drops the record, and a later install starts again. A store with a newer schema than the release fails this way. The next run's recovery of a first install killed during its migration does the same when its retry fails so.

### Remote hosts

On host B, the machine that receives relayed mentions, a person does this.

1. Install Namedrop on B as above, with B's Rex server running. On a Linux server the Rex config dir is `~/.config/rex` too, and `install.sh` reloads B's config only when it runs on B.
2. Start the agents on B in Rex blocks, activate each session, and name the agents, with `namedrop` in B's blocks, or from the palette of an app attached to B. That B's palette shows B's actions is inferred from Rex's docs and unverified.
3. To let A mention a terminal on B, create `<B's state>/relay/allow-terminals`. A terminal runs a relayed message as a shell command, so this is off by default. `namedrop doctor` on B says whether it is on.

On A, the person adds B with `rex hosts add devbox <endpoint>`, which goes to A's home, and checks it with `rex hosts check`. B needs A in its own hosts only to start new mentions to A. Replies flow back by A's pull. B's bridge must run for B to accept an item, and the module's guarded start runs it from B's server start. Doctor on A reports relay failures as `ND-RELAY-002` and `ND-RELAY-003`. PLAN's item 10 writes these steps into the user docs.

## Tradeoffs accepted

- **A process start per action.** Each action runs the binary once. The probe measured 0.03 s.
- **`python3` stays a requirement.** Herdr requires it too, and the installer checks for it.
- **Rex-first names are lost when Herdr is installed later.** The handoff says so, and Doctor counts the agents that still run the old hooks.
- **The palette is proven only by `--origin palette` until the operator's check.** The app attaches only to the default server.
- **Popup bounds are fractions of the window.** A screen of 72 columns in a narrow window wraps, and the layer cannot be sized in cells.
- **A broken module is silent at load.** `pcall` keeps it from rejecting the person's file, so the install's readback and Doctor, not Rex, report it.
- **The person's own key wins.** A key bound later in `init.lua` shadows Namedrop's, and Doctor says which.
- **The installer needs Rex running.** It asks the server which file it reads, reloads, and reads back, and edits nothing without a local server.
- **About Namedrop is in the palette.** Rex cannot hide an action, and the installer and Doctor need `namedrop_about` to prove which module loaded. From the palette it shows its result or nothing, which U14's operator step records.
- **A retired state's running agents go quiet.** After a handoff or a removal, an agent that still runs the old hooks gets no Namedrop messages until it restarts. Forwarding its hooks would act on a store that does not hold its session.

## Implementation plan

Every commit compiles, passes `cargo fmt --check`, `cargo clippy --locked --all-targets -D warnings` with and without `--all-features`, and `cargo test --locked --lib`, and ends in a state you can check with that commit alone. Live Rex checks run on the testbed's Rex lane, or on a scratch server under `env -i` with its own `HOME`, state, and `REX_SERVER` naming itself, on preview.14 and preview.18 both.

**[H]** marks a commit that touches a path Herdr also runs: the shared UI, the packages, activation, updates, or the archive. Before an [H] commit merges, `/verify` passes on real Herdr, the Herdr-in-Rex lane included, and its done-when includes the Herdr differential below, with the scenarios the commit names and the differences it pins. A commit that pins none says so.

**The Herdr differential.** U2, the first [H] commit, commits the harness that steps 4 and 5 ran from scratch directories, as `tests/differential/`: `flow.py` (the latest `flow3.py`), the script `herdr` it puts on `HERDR_BIN_PATH`, which logs every call with its location-shaped environment and arguments, typed text included, the copy of the launcher, and `cmp.py`. `flow.py BINARY OUT` builds an installed-runtime layout in a fresh profile, so every self-spawn goes through the launcher, and drives one Herdr space end to end. It writes one report: each step's exit, stdout, and stderr; every `herdr` call, as a set; every process the launcher started, with its arguments and environment, as a set; the processes still live at the end, as a set; and, new in U2, every file under the profile's `HOME` and state, by path, mode, and normalized text, with binary files and the store by path and mode only. The harness runs base and head three times each, and `cmp.py` compares the reports. Steps compare in order, with each line under its stream. Only the sections marked `(set)` compare as sets.

- **The base flow** (35 steps): `activate`; `name` for an agent, a second agent, and a terminal; two `address create`s; `reconcile`; the registration commands the prompts carry; a send to an agent and one to a terminal; four `@a@b`-shaped sends and a prompt; `delivery inbox`; the prompt hook, directly and through the installed wrapper; a deferred send and inbox under a sandbox that denies the socket; `reminder set`; `space pause`, `doctor`, and `space resume`; the status hook; the Stop hook; the mailbox wake; and `channels`, with a browser opener that only logs.

## Decisions

The first draft left four calls to the operator. They are made.

- **No Lua revision gate.** The Rust handshake is the only version gate, and its tested range widens per release. The module carries no revision, so it cannot refuse a server that the binary accepts.
- **A version-stable module.** The module holds names, titles, keys, `endpoint()`, and `namedrop_about`, and every other action calls `namedrop rex action`. A binary update cannot break a loaded module.
- **`init.lua` is edited, under guards.** `pcall(require, "namedrop");` goes in as line 1, under the six guards of [Editing `init.lua`](#the-installer), and `--print-config` edits nothing.
- **Keys are bound by default.** A key already bound is skipped, and Doctor reports the skipped keys and the keys in effect.
- **The palette check runs in a disposable macOS account** whose default Rex server is a test server. U14 writes it as an operator step.

## Open questions and risks

- **The palette may treat custom actions differently from the docs.** If the actions are missing from the palette, the keys and `rex do` still work, and the done-when is not met until Rex fixes it.
- **Rex is a preview.** Each release can change the API. The handshake settles on the highest revision that both sides offer, and refuses, with one error, a server that serves no revision in Namedrop's tested range. The range widens only after the probes of [What exists in Rex](#what-exists-in-rex) run again on the new release. A newer server that still serves a tested revision passes the handshake, and can still behave differently at that revision: preview.19 settles at 13 with U1 and fails two live tests there (the note on U1). So the handshake keeps out older and much newer servers, but not every change, and the live tests run again on each new Rex release.
- **The app's server environment is unmeasured.** The probe's server had `PATH=/usr/bin:/bin` and no `XDG_*`. The module names every program by its absolute path, so the app's `PATH` does not matter, and it passes `NAMEDROP_STATE_DIR`, so the install record is not read there. The app server's `HOME` decides its default socket and config path, which the installer reads from the server and does not guess. Doctor reports the server's `HOME`, `XDG_*`, and `REX_SERVER` through `namedrop_about` (U6), and U14's operator step records them.
- **A Herdr release from before step 6 takes no lock.** It can still rebake the packages over a standalone install. Doctor reports `ND-INSTALL-003` and names the fix, but nothing prevents it.
- **The installer edits the server it finds.** With `REX_SERVER` unset, that is the default socket for the installer's `HOME`, which is the app's server. A `REX_SERVER` that names another server, such as a testbed's, sends the install there, by design. Doctor and `rex.json` name the server, so a person who installed into the wrong one can see it.
- **A session that ended while its state was removed still counts.** Removal leaves the store's bindings active, and a retired state records no end. So an update that needs a session refresh, installed over a removed state, stays refused for such a session until a live state records the end. The refusal names it. No test covers a way out.
- **On Linux, a subreaper may adopt the checker's child.** The guard's parent test is measured only on macOS ([Release checks](#release-checks)).
